## 后端重部署（改代码/改环境变量后）

```bash
# 密钥在 ~/.s/access.yaml（AccessKey）和 D:\阿里云\.env（业务密钥）
bash deploy/deploy-fc.sh
```

- `deploy/fc/zhimai-api/s.yaml`：custom.debian10 + python3 index.py（vendor 依赖已打包）
- `deploy/fc/resume-analyze/s.yaml`：custom.debian10 + 官方 Nodejs20 层 + node server.js
- 端口约定 9000；http trigger anonymous 自动生成 *.fcapp.run 域名
- 依赖更新时：backend 需重打 `pip install -t vendor --platform manylinux2014_x86_64 --python-version 3.10 --only-binary=:all:`

## 前端发布（Qoder Sites）

```bash
cd frontend
# .env.production 写好两个 FC 地址和镜像地址后：
npm run build
# 在 qoder 会话里：prepare_site(dist) → publish_site → get_publish_status
```

发布/改公开策略须在 qoder 会话内用 sites 工具（CLI 单独调缺会话凭证）。
访问策略改公开：`get_site_access` → `update_access_policy`（public + confirmPublic=true）。

## 知识库镜像（CloudBase）

```bash
# 本地预览
python -m http.server 4310 --directory mirror/site

# 重新构建并发布（mirror/dist 为上传目录）
bash deploy/deploy-mirror.sh
```

- 镜像产物落盘为 `目录/index.html`；`source_url` 统一经 `backend/kb_source.py` 映射
- 链接规则：先解码 → 剥零宽字符 → `/index` 结尾收敛为同级 `index.html` → 重新编码
- 存量数据修正：`KB_SOURCE_BASE=... python ingest/rewrite_source_urls.py --dry-run`，确认后去掉 `--dry-run`
- CloudBase 默认测试域名首次访问会出现风险提醒页，点“确定访问”后继续；只有绑定已备案自定义域名才能彻底移除
- 原知识库站域名只允许出现在抓取脚本配置中，前端、接口和镜像 HTML 都不应出现

## 环境变量

| 位置 | 内容 |
|---|---|
| FC zhimai-api | SUPABASE_URL/SERVICE_KEY、DASHSCOPE_API_KEY、DEEPSEEK_API_KEY、ALLOWED_ORIGINS、QWEN_MODEL_CHAT、EMBEDDING_MODEL、MIN_RETRIEVE_SCORE、KB_SOURCE_BASE |
| FC resume-analyze | DEEPSEEK_API_KEY、ALLOWED_ORIGINS、PORT=9000 |
| 前端构建 | VITE_API_BASE、VITE_ANALYZE_URL、VITE_KB_SOURCE_BASE（写进 .env.production） |

## 故障速查

| 现象 | 原因 |
|---|---|
| CORS 报错 | ALLOWED_ORIGINS 没含 Sites 域名 → 改 .env 重跑 deploy-fc.sh |
| 首次请求慢 3-8s | FC 冷启动，正常 |
| 问答无来源 | Supabase key 失效/向量查询为空 |
| 来源 404 | 镜像未发布该文章，或 `KB_SOURCE_BASE`/`VITE_KB_SOURCE_BASE` 不一致 |
| 来源仍指向原站 | FC 的 `KB_SOURCE_BASE` 未注入，或前端构建没带 `VITE_KB_SOURCE_BASE` |
| 改写兜底文案 | DASHSCOPE_API_KEY 没注入或限流 |
| analyze 502 | DEEPSEEK_API_KEY 缺失且 engine=deepseek |
