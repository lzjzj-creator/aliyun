## 管理后台（#admin，密码保护）

公开站保持可评审；管理入口不放进导航，只通过隐藏地址进入：

```
https://zhimai-resume-uxvajmzewfe.qoder.zone/#admin
```

首次配置或改密码：

```bash
python ingest/make_admin_password.py            # 随机生成，写入本地 .env
python ingest/make_admin_password.py --rotate   # 换密码，同时让旧会话失效
bash deploy/deploy-fc.sh                        # 只把哈希和签名密钥下发 FC
```

- 密码只存在本地 `.env` 的 `ADMIN_PASSWORD`，不会打进前端包；线上校验 `ADMIN_PASSWORD_HASH`（PBKDF2-SHA256）
- 登录返回 HMAC 签名令牌，默认 2 小时过期，浏览器只存 sessionStorage；关标签页即退出
- 同一来源连续输错 5 次会暂停 5 分钟，避免公开接口被暴力尝试
- 管理接口：`POST /api/admin/login`、`GET /api/admin/overview`、`GET /api/admin/documents`、`POST /api/admin/cleanup`（v2 保留期核对，默认 dry_run）
- 未配置哈希/密钥时管理登录返回 503，公开问答与知识库镜像不受影响
- 静态托管本身没有鉴权，密码关卡由 FC 后端承担；不要把管理页改成纯前端判断

## 故障速查

| 现象 | 原因 |
|---|---|
| CORS 报错 | ALLOWED_ORIGINS 没含 Sites 域名 → 改 .env 重跑 deploy-fc.sh |
| 首次请求慢 3-8s | FC 冷启动，正常 |
| 问答无来源 | Supabase key 失效/向量查询为空 |
| 来源 404 | 镜像未发布该文章，或 `KB_SOURCE_BASE`/`VITE_KB_SOURCE_BASE` 不一致 |
| 来源仍指向原站 | FC 的 `KB_SOURCE_BASE` 未注入，或前端构建没带 `VITE_KB_SOURCE_BASE` |
| 改写兜底文案 | DASHSCOPE_API_KEY 没注入或限流 |
| analyze 502 | DEEPSEEK_API_KEY 缺失且 engine=deepseek |

## v2 上线顺序（迁移 → 冒烟 → 逐个开开关）

前置：`docs/v2-迁移验收记录.md` 的隔离库验收已通过（96/0）。验收通过 ≠ 线上已迁移，下面第 1 步之前线上没有 v2 表。

1. **应用迁移**（SQL Editor 以 `postgres` 执行，或 PAT 走管理 API），顺序固定：
   `supabase/migrations/20261117_v2_memory.sql` → `supabase/migrations/20261118_v2_quota.sql`。
   两个文件都自包含（建表 + 触发器 + RPC + RLS/授权），不含 pg_cron 假设，也不碰 v1 的 `documents`/`chunks`。
   应用后立即在隔离库那套断言的线上版上复跑一次关键项：零策略可读性、`service_role` 可调 RPC、dry-run 清理返回 0。
2. **保持开关为 0 部署一次**：`bash deploy/deploy-fc.sh`，此时 v2 路由不挂载，线上行为与 v1 完全一致，用来确认环境变量注入没把服务弄坏。
3. **只开 `V2_MEMORY_ENABLED=1`**：再部署一次，冒烟 `POST /api/v2/sessions` → `GET /api/v2/sessions` → `POST /api/v2/messages`，
   确认响应里没有 `session_token_hash`，浏览器与日志里都不出现 service key。
4. **再开 `COACH_ENABLED=1`**：访谈引擎上线，日 token 预算 `COACH_DAILY_TOKEN_BUDGET`（默认 200000）生效；
   首轮先人工跑一轮真实对话，看首 token 与整轮延迟。
5. **开 `V2_SHARED_QUOTA=1`**（多实例必须）：anon 轮次配额、单会话流互斥、日 token 预算改由库里结算，
   `instanceConcurrency: 50` 的并发不再被进程内桶误伤；配额存储故障时 fail-closed 返回 503，而不是悄悄放开闸门。
   注意：没应用 `20261118_v2_quota.sql` 就打开这个开关，所有 v2 写请求都会 503。
6. **v2 入口对访客可见**：前端发布 v2 访谈入口。v1 问答路径不删不改（`/api/chat/stream` 保留），
   切换只发生在前端默认入口，v1 就是回滚面，因此不做按比例灰度。
7. **注册定时清理**：`20261118_v2_cleanup_schedule.sql`（pg_cron，会先干跑再注册两个作业），
   或自建定时器/人工调用 `POST /api/admin/cleanup`（默认 dry_run，只回计数）。
   次日检查 `select status, return_message from cron.job_run_details order by start_time desc limit 5;` 出现 success。
8. **回滚**：把对应开关置 0 重跑 `deploy-fc.sh`，前端退回 v1 入口即可。数据无需回滚（v2 三表对 v1 无影响）；
   确认不再上线时才按 `supabase/migrations/rollback/` 的反向顺序清库。
   发布瞬间的在途请求：v1 问答不落库、刷新即恢复；v2 访谈可能留下 `status=streaming` 的悬挂行，
   由后续 `done/error` 改写或 90 天作业清理——所以选低峰期发版，别在评审进行中发。

环境变量下发方式：`deploy/deploy-fc.sh` 从 `.env` 读取并为缺失项兜底（默认全 0），`s.yaml` 用 `${env(...)}` 注入 FC；
只改开关也必须重跑部署脚本，控制台改环境变量容易被下次 `s deploy` 覆盖。
