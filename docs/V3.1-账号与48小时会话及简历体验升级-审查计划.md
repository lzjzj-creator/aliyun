## 一、建议先审的核心结论

建议保留现有 Vue 3 + FastAPI + Supabase 架构，做增量升级，不为参考 React 开源项目而重写整个 V3。

本次升级分为四条工作线：

1. **续访与历史**：不做账号；访问者凭浏览器本地凭据（`zm_anon_id` + 每会话令牌）在 48 小时保留期内恢复对话；换浏览器或清站点数据即新身份，属隐私特性。
2. **管理后台**：扩展现有知识库后台的运营概览；无账号体系后不建用户列表/登录记录，仅保留管理员操作审计（可独立小项）。
3. **简历成品质量**：区分编辑提示与正式投递内容，去除黄色框、对比底色、操作焦点和内部说明；将截图型 PDF 升级为文本型 PDF，解决分页及中文字体问题。
4. **前端体验**：参考魔方简历、超级简历和 FlowCV，把聊天、简历库、编辑预览组织为清晰的工作台；会话页明示「历史保存在本浏览器」。

优先让简历“能放心投递”；去账号化后无外部采购/备案前置，所有工作线均可在现有基础设施上直接开工。

### 审查用默认假设，尚非最终产品决定

| 决策 | 本计划建议 | 理由与边界 |
|---|---|---|
| 续访方式 | 浏览器本地凭据（`zm_anon_id` + 每会话令牌），不做账号/验证码登录 | 现状已实现；换浏览器/清缓存即新身份属隐私特性；若未来需多设备恢复再立 V3.2 |
| 48 小时含义 | 原始消息自服务器创建时间起保留 48 小时 | 不是“每次登录重置计时”，也不是“持续聊天就无限延长旧消息” |
| 简历与长期记忆 | 与聊天保留期分开，不因聊天满 48 小时就删除用户已保存的简历 | 维持现有长期数据生命周期，明确告知并获得必要同意；不能宣称所有个人数据 48 小时清空 |
| 管理员权限 | 现有 env 密码后台 + 操作审计；默认不开放聊天正文 | 无账号体系，后台不建用户列表 |
| 发布方式 | 每个里程碑验收后发布，不把所有变更一次性压入生产 | 降低清理规则与 PDF 引擎同时变化的风险 |

## 五、本地凭据续访与安全方案（去账号化修订）

> 2026-11-22 拍板修订：**取消账号/登录系统**，访问者聊天记录通过浏览器本地凭据续访。原 §5 的邮箱/手机验证码、Supabase Auth、凭据认领、账号绑定等内容整体移出本轮范围；若未来需要多设备账号，可作为 V3.2 另行立项。

### 5.1 续访机制（现状已实现，仅需验收）

现有前端已具备完整的本机续访凭据，无需新增账号体系：

| 本机凭据 | 存储位置 | 作用 |
|---|---|---|
| `zm_anon_id` | localStorage | 稳定的匿名身份，关浏览器不丢 |
| `zm_session_tokens` | localStorage | 每个会话独立的访问令牌（服务端只认持有者） |
| `zm_current_session` | localStorage | 上次打开的会话指针 |
| `resume_draft_*` | localStorage | 简历草稿（本就不落服务端） |

回访路径：同一浏览器 → 同一 `anon_id` → `GET /api/v2/sessions` 列出未过期会话 → 凭本地 token 打开详情。**关闭/退出浏览器再访问，历史自动恢复**，无需任何登录动作。

### 5.2 边界与 UX 要求

- 换浏览器/设备、清理站点数据 = 新匿名身份；旧会话标题可见但详情令牌已失——这是隐私特性而非缺陷。
- 会话页须有一句明示：「历史保存在本浏览器，清理浏览器数据后将无法恢复」。
- 服务器 48 小时到期删除是权威删除；此后本机残留的 session_id/token 成为死键，前端遇 404 应提示「已过期」并自动清理死键。
- localStorage 只存指针与令牌，不缓存聊天正文——服务端删除后本机不留正文残留（需回归测试确认）。

### 5.3 安全影响（去账号化后整面撤销）

- 撤销项：验证码限流、邮件滥发、账号枚举、凭据认领并发、`app_sessions`/`login_events`/角色表、`auth.users` 接入——**§5.2 原 P0 硬性门槛（SMTP/域名备案/Cookie 同域）整体失效，不再需要域名与邮件通道**。
- 保留项：`X-Session-Token` 仍是每会话 bearer 凭据；列表/详情/写删的所有权校验照旧；IP 限流照旧。
- 管理后台维持现有 env 密码 + 内存会话，不接入用户体系；管理员操作审计可作为独立小项保留。
- 长期记忆（v3 owner_token）与聊天续访互相独立，用户可随时禁用/找回，与是否登录无关。

### 5.4 数据库增量（修订后）

| 表/对象 | 变更职责 |
|---|---|
| `chat_sessions` | 不变（仍按 anon_id 归属） |
| `chat_messages` | 增加可索引的过期时间（48h 清扫唯一必需的结构变更） |
| 其余 | 无新增——无 `auth.users`、`app_sessions`、`login_events`、角色表 |


## 六、48 小时记录的完整生命周期

### 6.1 建议采用的明确规则

**采用理由（产品定位）**：48 小时原始消息保留是**隐私卖点**而非成本优化——与"长期记忆需明示同意、原文证据可追溯/可剥除"构成一致的隐私叙事：原始对话短留，结构化事实经用户确认后长留。这决定了必须采用严格口径（按消息创建时刻计），否则"放宽到会话闲置 48h"会让持续活跃会话无限留存原文，破坏卖点。

**行业先例**（本口径非自创）：GetStream Chat 保留策略按消息各自 `created_at` 过期并硬删；Linq 的 24 小时窗口同样从创建时刻起算、与投递/已读无关。两者均与用户文案区分"到期不可读"与"后台物理清除"。

以服务器 UTC 时间计算：`expires_at = message.created_at + 48h`。

例如 11 月 21 日 14:00 创建的消息，在 11 月 23 日 14:00 到期；11 月 22 日重新登录、打开网页或浏览历史，都不延长它的寿命。新消息有自己的到期时间。

如果产品实际想要“最后一轮对话结束后整段会话再保留 48 小时”，可以改为另一套规则，但这会让持续活跃会话中的旧消息保存超过 48 小时，必须在文案中直说。两种定义不能混用。

### 6.2 读取保护与物理清理分开

- 读取：到期即不得从列表、详情、搜索、导出、简历素材读取及模型上下文重新取得。
- 模型状态：清理或重建基于已过期原文生成的会话画像、摘要和缓存，避免原文删除了却通过摘要继续保留。
- 后台清理：拟每 5 分钟执行一次幂等任务，正常情况下到期后 15 分钟内完成在线主存储清理；任务失败需告警并可重试。
- 多实例清扫采用行业标准模式：`chat_messages.expires_at` 上建部分索引（`WHERE expires_at IS NOT NULL`），清扫事务 `SELECT ... FOR UPDATE SKIP LOCKED` 批量认领行，多个工作实例并发不互相踩；大批量删除分批提交，避免长事务与死元组堆积。
- 不把清理任务放在会休眠或扩容的 Web 实例计时器里。
- 用户主动删除与自动过期复用一致的删除规则，区分“删除一段聊天”和“删除所有个人数据”。

不能把“每 5 分钟跑一次删除”描述成“48 小时整物理擦除”。对用户的准确承诺应是：到期不可访问，后台按已声明的清理周期清除；备份、访问日志另有保留规则。

### 6.3 各类数据边界

| 数据类别 | 本计划建议 |
|---|---|
| 聊天原文及直接携带原文的缓存 | 48 小时；所有读取入口统一过滤 |
| 会话标题、未另行同意保留的摘要/画像 | 随来源过期更新或清除，不能残留首句敏感信息 |
| 原文出处、引用片段、版本快照内的原文证据 | 同步处理；不要只删 `chat_messages` |
| 用户明确保存的简历正文 | 不随原始聊天过期而自动删除，继续受简历自身保存/删除政策约束 |
| 明确同意保存的长期事实 | 与原始聊天区分；原文引用到期后移除，保留经过许可的结构化事实，并标注原始出处已过期 |
| 账号本身 | 不因 48 小时未使用而注销 |
| 登录/管理审计 | 独立政策；业务后台可先建议展示近 30 天，但正式保留期须结合适用要求确认 |
| 数据库备份及基础设施日志 | 核查平台实际保留期；避免记录聊天全文，并建立恢复后重放删除规则的流程 |

现有 V3 365 天无活动清理策略不在本次未经批准缩短。界面应说明：聊天仅保留 48 小时，用户另行保存的简历和已同意的长期记忆不是同一保存规则。

### 6.4 不丢消息与正确恢复

- 用户消息先可靠入库；AI 回复完成后保存正式内容，途中中断则记录可辨认的失败/中断状态。
- 保留 client_msg_id 等幂等键，断线重试不重复插入。
- 不能仅在网页卸载事件或“关闭页面前”保存。
- 同账号多设备按服务器版本读取；切换账号时不能展示上一账号的缓存或草稿。
- 保存失败应明确提示，不能显示“已保存”；数据库不可用时不能退回不受账号隔离的匿名数据。

## 七、简历排版与导出专项

### 7.1 第一目标：正式文件没有编辑器痕迹

建立三层分离：

1. **事实和字段层**：姓名、经历、技能、日期、已确认的成果。
2. **编辑辅助层**：缺失提醒、出处、优化解释、前后对比和选中态。
3. **正式渲染层**：仅接收允许投递的字段及版式配置，不将第二层混入文档。

实现时优先复用同一套纯简历渲染组件及排版参数，通过编辑器在纸面外加提示；不是复制两套长期分叉的 HTML，也不是导出前临时对整个页面强制“背景全白”。

正式 PDF 排除 `.gap`、`.compared`、`.hl`、按钮、占位文本、调试信息、生成说明、版本标签、出处批注、网页 URL/日期页眉及预览阴影。合理的分隔线仍保留，不能将真正的简历内容一并清除。

### 7.2 缺失事实不能靠“去掉注释”掩盖

- 核心必填字段缺失：导出前列出问题，引导补全。
- 可选空区块：正式版隐藏，不输出“待补充”整节。
- 带 `【待补充】` 的不完整句子：由用户补齐、删除该条或退回有事实依据的原文。
- 不能只删掉占位标记，留下看似完整但语义错误的成果描述。
- 原文出处和优化解释继续可在编辑器查看，不印进正式简历。
- 不使用 AI 自动补造公司、日期、指标或奖项来填满版面。

### 7.3 模板首期只做两套

| 模板 | 适用场景 | 特点 |
|---|---|---|
| 中文经典单栏 | 校招、实习、通用投递 | 教育/项目/实习层级清晰，黑白为主，细分隔线，默认模板 |
| 中文现代单栏 | 社招、产品、技术岗位 | 经历优先，可选克制的深色章节强调，信息密度更有弹性 |

先不做复杂双栏、时间轴、能力进度条及装饰性图表。照片作为可选信息，默认不要求；不增加无必要的年龄、婚姻等字段。

建议起始排版参数，最终以真实样张审查为准：

- 纸张固定 A4，210 × 297mm，不随浏览器视口重排。
- 页边距约 12–16mm；正文约 10.5–11.5pt；行距约 1.35–1.5。
- 姓名约 20–24pt，章节标题约 12–13pt。
- 单位/项目名突出，日期右对齐；长标题自动换行，不覆盖日期。
- 统一中英文与数字的基线、标点、项目符号和间距。
- 技术栈优先用文本行，不默认使用灰色胶囊框。
- 支持自然两页；不能为了“一页”自动缩到难以阅读或裁掉内容。
- 长条目允许在合理位置跨页；章节标题不能孤立在页尾，不对超过一页的整节机械设置禁止分页。

### 7.4 导出技术选择

推荐先做 **固定模板 HTML/CSS + 受控 Chromium/Playwright 生成文本型 PDF** 的验证，再正式接入。它适合保留 Vue 与现有前端样式体系，不必为了 React-PDF 或其他项目的框架重写编辑器。

对照方案：

- 浏览器系统打印：成本低，但受用户设置、浏览器和移动端支持影响，不能作为“一键直接下载”的唯一保证。
- WeasyPrint 等纯 Python 渲染：无浏览器依赖，但已知 CJK 字体地雷——部分字体子集嵌入为 CID Type 0C 后 **macOS Preview / Adobe Reader 无法渲染**，且不支持 Grid/Flex 完整特性；若考虑此路线须先在真实阅读器验证。
- Typst/RenderCV 等独立排版引擎：值得比较质量，但会增加样式重写、预览同步及部署成本，首版不直接引入第二套完整引擎。
- html2canvas 截图 PDF：可以做紧急去标记修复，不能作为最终投递格式继续依赖。

具体要求：

1. 导出服务从经过授权的文档 ID 和确定版本读取数据；先完成保存或形成明确快照，避免导出旧稿。
2. 前端预览与服务器渲染共用模板组件、模板版本、字体与版式参数；导出包跟应用构建一并固定。
3. 服务端使用固定 A4 画布、print CSS，等待字体加载及页面布局稳定，关闭浏览器默认页眉页脚。
4. PDF 文字可选择、搜索和复制；嵌入合法可分发的中文字体，检查中英文混排与缺字。
5. 图片缩放不影响文字层；不以“全页一张图片”冒充文本型 PDF。
6. 用户内容按文本或允许的富文本子集渲染；不接收任意 HTML、脚本、URL 作为渲染入口，阻断 XSS 与 SSRF。
7. 字体和必需资源优先随服务提供；外链头像等必须经过受控处理，不任意访问内网或公网地址。
8. 限制单份内容大小、渲染时长与并发；临时文件按任务清理，不提供公共可猜测下载链接。
9. 先验证当前后端容器资源、冷启动和并发能力，再决定同容器部署还是独立渲染服务，避免未经测量提前拆微服务。
10. “ATS 友好”通过文本提取与阅读顺序测试给出证据，不承诺兼容所有招聘系统。

## 八、前端重组方案

### 8.1 信息架构

```text
本机身份（localStorage 凭据，无登录页）
  └─ 工作台
       ├─ 对话：最近 48 小时历史、继续对话、新建
       ├─ 我的简历：新建、复制、编辑、版本、导出
       ├─ 我的素材：既有长期记忆与事实确认，清楚说明保存政策
       └─ 账号与隐私：删除聊天、关闭长期记忆、删除个人数据

管理后台：只向被服务端授权的管理员展示
  ├─ 概览
  ├─ 用户
  ├─ 登录记录
  └─ 现有知识库管理
```

### 8.2 简历编辑工作台

桌面端采用“区块导航 + 内容编辑 + A4 预览”，但不强制所有设备同时显示三栏：

- 章节可切换，内容和样式设置分开。
- 主操作固定为保存状态、预览与导出，减少重复按钮。
- 修改即时反映到预览，支持撤销及现有版本能力；先验证当前版本保存逻辑再扩展。
- 出处、AI 建议、缺失项放在侧栏或折叠面板；默认正式预览无彩色覆盖。
- 笔记本宽度不足时收起章节栏；移动端切换“编辑/预览”，不将三列挤在一起。
- 手机预览是固定纸面的缩放显示，不改变 PDF 的实际文字宽度。
- 加载、保存中、保存失败、空状态、登录失效、会话过期都要有明确反馈。

视觉方向为克制的白/浅灰工作区、明确文字层级与单一强调色；网页控件与简历纸面使用不同样式范围。复用现有品牌，不另做无必要的大规模主题替换。

交互验收包括键盘操作、可见焦点、表单标签、错误信息、足够点击区域和正文对比度。黄色提示在编辑器里可以保留，但不能仅用颜色表示状态，也不能进入投递文件。

## 九、管理后台的最小交付范围

### 用户列表

显示账号标识、脱敏邮箱/手机号、注册时间、最近成功登录时间、状态。支持搜索、分页和时间筛选。首版无需精确地理位置或设备指纹追踪。

### 登录记录

显示账号、登录时间、认证方式、成功/失败、必要设备摘要；失败事件无法可靠对应账号时不能强行归因。IP 如确有安全需要则限制访问并脱敏，不默认展示完整地址。

记录以可信认证结果为准，不能由浏览器随意提交“登录成功”。令牌刷新与打开页面不重复算作新登录；“最近活跃”与“最近登录”分开展示，不冒充实时在线人数。

### 管理动作

首版支持禁用/恢复账户、撤销应用会话，并记录操作者、对象、时间和结果。明确普通用户不能调用这些 API；管理员权限通过受控方式授予，不开放公共管理员注册。

原有知识库管理保留。现状如实说明：现有管理员认证是**环境变量密码换发自定义内存会话**（`backend/admin.py` 的 `admin_login`/`verify_session`），不属于任何正式账号体系——扩展后台时应同时把管理员认证升级为服务端角色校验的账号会话，与旧凭据的切换先验证新入口可用再撤销；历史令牌不能无限保留为绕过新权限的后门。

不默认增加查看聊天全文、批量下载用户简历、广告追踪或复杂 BI 报表；若后续确有业务需要，另审权限、告知与审计方案。

## 十一、硬性验收清单

### A. 登录与数据隔离

- [ ] 账号 A 登录并产生对话；关闭网页后重新登录仍可恢复未过期记录。
- [ ] 同一账号换浏览器/设备可恢复；无需复制旧 localStorage。
- [ ] A 退出，B 登录；页面、缓存、接口、导出都不出现 A 的数据。
- [ ] 猜测或替换 session_id、owner_id、doc_id、历史版本 ID，不能越权。
- [ ] 匿名认领需同时证明新旧身份；并发认领不会抢占、重复绑定或覆盖。
- [ ] 退出或禁用后，旧登录会话和被绑定资源的旧匿名凭据不能继续访问。
- [ ] 管理员页面与 API 双重受限，角色不能从客户端自赋。

### B. 48 小时

- [ ] 47 小时 59 分仍可读，达到 48 小时不可读；使用可控制的服务器时间测试，而非等待两天。
- [ ] 重新登录、打开页面、写入新消息不会延长旧消息的保留时间。
- [ ] 定时任务暂时失败时，过期内容仍不能经业务接口或模型上下文返回。
- [ ] 标题、摘要、画像、原文引用、缓存与版本证据没有遗漏。
- [ ] 已明确保存的简历不被对话清理误删。
- [ ] 断网、流式中断、保存失败、重试、多实例和并发清理不会造成误报保存成功或重复消息。

### C. 简历与 PDF

- [ ] 正式文件无黄色框、对比底色、焦点框、内部说明、占位提示和网页页眉页脚。
- [ ] 文字可复制、搜索；提取顺序合理，中文无缺字方框或乱码。
- [ ] 1 页、2 页、长项目、长中英文标题、长链接、缺失可选区块、照片有/无均通过。
- [ ] 标题不孤立、日期不重叠、段落不被截图式切断，不出现意外空白页或窄列长页。
- [ ] 相同内容在手机、窄窗口、桌面窗口导出，页面尺寸与版式相同。
- [ ] 预览与最终 PDF 的内容、字体、字号和模板版本一致。
- [ ] 至少在浏览器 PDF 阅读器及一种常见桌面阅读器/打印预览中检查。
- [ ] 不以编造事实、静默删经历或无限缩小字号来达到“一页”。

建议建立不少于 12 份脱敏/合成样例，覆盖中文校招、社招、中英混排、多页及极端字段。每份保留文本提取断言和 PDF 渲染截图，后续变更做回归比较。ATS 证据可使用 [Resume-Matcher](https://github.com/srbhr/Resume-Matcher)（Apache-2.0）等开源解析器做文本提取与字段识别回归，不空口宣称兼容。

### D. 运维与发布

- [ ] 邮件投递、实际域名 Cookie/CORS、前后端重启及多实例访问经过验证。
- [ ] PDF 生成错误、超时、并发与内存数据有可观察记录，不在日志中包含简历正文。
- [ ] 清理任务有最近成功时间、删除计数与失败告警。
- [ ] 原知识库、访谈、事实确认、简历复制/版本/优化流程不回归。

## 十二、生产迁移与回滚边界

1. 先核查生产数据库结构和实际数据量，再做可回滚的增量迁移；不直接修改已执行的历史迁移文件。
2. 账号绑定先经过测试环境、少量授权测试账号验证，再放开正式入口。
3. 90 天改 48 小时是数据保留政策变化：先明确生效日及历史数据处理口径，对将被清理的记录做计数 dry-run，审核后才执行。
4. 不自动给所有历史对话延长保存期，也不未经告知突然删除既有记录；旧数据如何过渡必须审定。
5. 分别验证旧匿名入口、新账号入口和管理员入口的权限收口，迁移结束后移除不再需要的旧凭据访问通道。
6. 应用回滚与数据回滚分开：版本可以回退，已经按政策删除的聊天不能靠回滚应用恢复。
7. 若从备份恢复数据库，必须重放删除/到期规则，防止过期或已主动删除的数据重新出现。
8. 生产迁移、删除、配置和部署均需单独确认；本计划不是对这些操作的预先授权。
